11. Correction, real ML models, approach-risk briefing, and a Google-like map

11.1 Correction: the flaky watch test was not a test-scheduler artefact

§10.6 recorded a mechanism that had not been measured, and the "fix" derived from it was wrong:

  • The claim: Robolectric's one-off instrumentation cost was expiring the 5 s awaitUntil default, and Room posts its invalidation callbacks to the paused main looper, so awaitUntil was changed to call ShadowLooper.idleMainLooper() on every poll.
  • Measured instead of assumed: a temporary diagnostic printed the outbox row and the collected Flow every 250 ms. The row reaches SENT and the Flow reports it within ~125 ms, with no main-looper draining at all — Room refreshes invalidations on its own query executor, so the drain was never needed.
  • The drain was actively harmful. Called from the main thread inside runBlocking, idleMainLooper() cost roughly 1.5 s per call and starved the very background work being awaited. With the drain in place the "SOS delivered" test spent its entire 60 s ceiling inside the loop, and the sibling SOS test took 24 s where it should take under a second. The drain is now removed, and awaitUntil is a plain real-time poll.

11.2 The actual cause: the C: drive was full

Three symptoms that all pointed the same way, once they were noticed together:

  • Copy-Item failed with "There is not enough space on the disk."
  • Get-Content -Raw returned nothing for a file that [xml] had just parsed successfully.
  • A test report declared failures="5" but contained no failure text at all — the write had been truncated.

C: had 0 bytes free out of 96.8 GB. The build, the JDK, the Android SDK and GRADLE_USER_HOME all live on D:, but JVM temp files, Robolectric's scratch space and the test-report writes go to C: through %LOCALAPPDATA%\Temp. Freed by clearing the recycle bin (796 MB) and the npm cache (4.55 GB) → 5.28 GB free. Three consecutive full-suite runs then passed with no change to any test.

The flakiness was never in the SOS code, the Room flows, or the coroutine scheduling. Honest note: this is an environment defect, not a code fix, and four three-minute test cycles were spent on hypotheses before free disk space was checked — which should have been the first thing to check on a machine that reports "not enough space".

11.3 A real ordering guard in the watch controller (kept, but not the cause)

While the flake was still unexplained, WatchController was also changed, and those changes are kept because they stand on their own merits:

  • After flush() returns, the controller re-reads the outbox row and updates the face directly, instead of waiting for Room's change notification. This removes a real latency: the watch face no longer sits on "Queued on the device" for an SOS that has already been delivered.
  • SosDeliveryState.afterObserving(...) makes a settled DELIVERED/FAILED outcome sticky for its own event, so a late "still queued" observation cannot walk the indicator backwards, while a newly raised SOS still resets it. Pinned by SosDeliveryStateTest (4 tests).

It is not claimed to have fixed the flake. §11.2 was the cause. The ordering rule is a guard against an interleaving Room is permitted to produce, not a bug that was observed.

Earlier rounds built the durable outbox, the payloads, and an honest NoBackendTransport that refused to pretend an event had been delivered. But the app could never actually talk to anything, for a reason that was not a missing feature but a wiring bug:

DELIVERED Delivered (ack id) the authority stored it
DUPLICATE Delivered idempotency: the server already has it
REJECTED (or HTTP 400/422) Rejected with the reason the same bytes can never be accepted

404 / 409 / 5xx / IO error / malformed body Retry could be a misconfiguration; never discard

14. The future-event risk model: a real supervised prediction, trained on real falls (2026-10-18)

The one thing the brief asked for that this project had repeatedly, correctly declined to fake. Section 13.4 said: "no fabricated 'future-risk' model — no outcome labels exist". That statement was right about the four named datasets, and it stayed right. This round changed the dataset, not the honesty.

14.1 The problem, restated

GeoLife, UCI HAR, OpenStreetMap and OpenWeatherMap/Open-Meteo contain no injury, incident or danger outcome at all. A supervised tourist-incident model is therefore impossible from them, and manufacturing labels would be fabrication. Two honest options existed: ship nothing, or find a dataset with real outcome labels. This round did the latter, documented the swap, and re-checked §13.4's blunt claim about the dashboard.

The other real gap found this round: the authority backend had no table that could hold a prediction. It stored incidents (events) and an SOS workflow (sos_alerts), and the dashboard could therefore neither receive nor display a prediction even if one existed. That gap is now closed (§14.4).

14.2 The dataset, and what was found in it

UniMiB SHAR (Micucci, Mobilio, Napoletano, 2017): 30 subjects, 9 activities of daily living and 8 real fall types, 50 Hz phone accelerometer. Downloaded here and verified by hash: 266,206,080 bytes, SHA-256 365a3967...67160.

  • 1,980 trials read, 1,979 used. Subject 10 / Jumping / trial 1 has 9,369 of 9,624 non-finite values. It was dropped, counted and reported in dataset_provenance.json — not interpolated, not mean-filled. A NaN in a feature vector would have poisoned every tree that touched it.
  • 6 fall trials never reach the 2.0 g impact threshold and are excluded from the positives (counted).
  • No OSI licence exists for this dataset. The provenance file records {"osi_approved": false, "research_use_only": true} plus the citation rather than inventing terms. Only derived artefacts are redistributed — never the recordings.

14.3 The target, the horizon, and the leakage proof

Given the last second of phone accelerometer data, will a hard fall impact land within the next second?

  • Positive = a window ending 1..50 samples before a sample that is the trial's argmax(magnitude) and is at least 2.0 g (reusing the app's own FallPolicy.MIN_IMPACT_G). Negative = a window cut at the same 0.2 s cadence from an ADL trial. Post-impact windows are a diagnostic, never training data.
  • Horizon and feature window are both 50 samples = 1.0 s — the longest fully supported horizon (trials run 151–446 samples, impact around index ~120, leaving ≥95 pre-impact samples). A 30-minute horizon is not attempted, and the docs say why.
  • Leakage is proved, not asserted. A window ending at t uses [t-49, t]; the label asks about (t, t+50] — disjoint by construction. train.check_no_future_information() re-derives this from the raw recordings on every run, and a shuffled-label control scores ROC-AUC 0.477 (chance).
  • No fitted preprocessing at all: every feature is scale-free within its own window, so there is no scaler that could carry a global mean from train into test.
  • Subject-disjoint 60/20/20, seed 42 -> 18/6/6 subjects, disjoint: true, 51,128 windows (6,458 positive / 44,670 negative).

15. Self-service tourist registration: the tourist creates their own account (2026-10-18)

Until this round every tourist account had to be created by an officer at the dashboard, and the tourist then signed in with an id and a one-time password. That is the wrong shape for the thing being built: a tourist who installs the app, with nobody at a desk, could not use the service at all. This round adds the one journey that was missing — the tourist registers themselves — and makes the result show up on the authority's screen with no officer action.

15.1 What "register" had to mean

Three constraints shaped the design:

  • the Tourist ID is the account's permanent name and has to look like one (TR-2026-00124), and the tourist has to be able to write it down — so it must be shown, and it must be copyable;
  • it must be unique by construction, not by a client-side counter that two phones can race;
  • the PIN is a credential: hashed like a password, never stored in the clear, never returned, never logged.

15.2 The ID is minted by the database, not the client

A client-side counter is the classic bug here: two phones registering in the same second both compute "00124". The allocation instead happens in SQLite:

  • a new table, tourist_id_sequence (id INTEGER PRIMARY KEY AUTOINCREMENT, issued_at INTEGER NOT NULL), where each registration inserts one row and reads back the number SQLite issued;
  • the text id is TR-<current UTC year>-<5-digit zero-padded number>, and tourists.id is the primary key, so even a text collision cannot create a duplicate — the code steps over to the next number;
  • the counter is never reset, across years or restarts. The year is for a human to read, not a reset boundary.

backend/tests/test_registration.py registers twelve tourists in a row and asserts twelve distinct ids; it also forces a collision and asserts the code moves to the next number rather than failing.

15.3 The PIN is the credential; the response carries no secret

The tourists table has NOT NULL password_salt / password_hash columns from the officer-created flow. Registration keeps that schema (no migration risk to existing rows) by writing a randomly generated secret that is immediately discarded into those columns; the account's real credential is the PIN, run through the project's existing scrypt hash_password. Neither the PIN, nor its salt, nor its digest is ever written to a response or a log — test_registration.py asserts the response contains the id and the account's public fields and nothing that looks like a secret, and test_security.py's rule (no hash or salt leaves the server) is unchanged.

The response to a successful registration is deliberately only:

{"tourist": {"touristId": "TR-2026-00124", "displayName": "…", "phone": "…",
             "registeredAtMillis": 1792305616556, "registrationSource": "SELF",
             "emergencyContactCount": 1},
 "note": "Registration complete. Sign in with this Tourist ID and the PIN you chose. …",
 "serverTimeMillis": 1792305616556}

No token: registering does not sign you in. The tourist signs in as a separate step, exactly so the id on the success screen is something they must keep.

15.4 One public write, and the privilege escalation it refuses

POST /api/v1/auth/register is the only new route and the only public write. It is fenced by reading as little as possible:

  • it creates only tourists rows;
  • it reads no privilege field. A body carrying "role": "authority" is refused with 400, and there is no field that could grant one — the escalation path does not exist rather than being blocked;
  • it issues no session, so it cannot be used to obtain a token;
  • it is idempotent per person, not per call: a phone number that is already registered is 409.

The validation is pure and lives in one place, backend/tsm/registration.py, reusing the existing hash_password (scrypt) and the same contacts validator the outbox uses (payloads.normalise("CONTACTS", …)), so a contact accepted here is a contact the sync path would accept.

15.5 The app: register -> get the id -> sign in

The Authority screen's sign-in card now has two modes, deliberately separate — Sign in and Register as tourist — because one creates the account and the other uses it. Registering collects a name, a phone number, a chosen PIN and its confirmation, and any number of emergency contacts (added one at a time, each with a name, a number and an optional relationship; removable). The form is validated on the phone first so a mistyped confirmation is answered instantly instead of costing a round-trip; the server validates everything again and its 409 is shown as "already registered" rather than as a generic failure.

On success the screen becomes a registration-success card showing the Tourist ID in a monospace readout with a Copy Tourist ID button, the account's name and phone, and a plain-language instruction on how to sign in next — including that the PIN is not shown again and that a forgotten PIN means an officer must reset it. Continue to sign in carries the id into the sign-in field and clears the PIN fields.

New code: authority/RegistrationForm.kt (pure validation), AuthorityContract.kt / AuthorityApi.kt / AuthorityClient.kt (request and response codec), AuthorityViewModel.kt (the state machine and the "a later failure must not erase an id still being copied" rule), and ui/screens/AuthorityScreen.kt (the mode toggle, the form and the success card).

15.6 The dashboard: Registered Tourists, with registration separate from tracking

GET /api/v1/authority/tourists was enriched (additively — nothing existing changed shape) and the dashboard's "Tourists" panel became "Registered Tourists", driven from it. Each row now carries:

touristId, displayName, phone, registeredAtMillis, registrationStatus, registrationSource (SELF for an app registration, the officer's id for a desk account, null for older rows), trackingStatus, lastSeenMillis, hasPosition, latestPosition, emergencyContactCount, openSosCount, latestRiskBand, latestRiskAtMillis, state.

The point of the split is that three different facts stay three different facts:

  • registration — is this a real account? (REGISTERED);
  • tracking — have we heard from the phone? (AWAITING_FIRST_REPORT, later OK/STALE);
  • safety — the open SOS count and the latest risk band, which were already there.

A tourist who has registered but never reported reads "Location not yet available"; the panel never shows a position that does not exist. New registrations appear at the top of the list on the next refresh (the list is newest-first) with no officer action.

16. Round: two-role sign-in, and the submit button that was dead on a fresh install

16.1 The report

A phone with a fresh install of the previous APK opened on the Authority screen showing NOT SIGNED IN, with Sign in with PIN and Create my account both greyed out. Nothing on the screen said why, and no Tourist ID was ever minted — so registration was, from the user's side, impossible.

16.2 The root cause, exactly

AuthorityScreen.kt enabled all three of Save address, Sign in and Register with

enabled = !busy && address.isNotBlank()

address was seeded from the stored session's baseUrl, which is empty on a fresh install. So the first thing a new user met was three dead buttons whose only requirement was a backend address that the app never asked for and never explained. It was not a registration bug, not a credential bug and not a network bug: the submission controls were gated on a field the tourist was never meant to fill in.

Two structural problems fell out of the same design:

  • the tourist's sign-in/registration and the operator's backend configuration lived on one screen; and
  • the operator's screen was reachable from the tourist's path at all.

16.3 What changed

  1. The gate moved to form validity. RegistrationForm.fieldErrors(...) reports a problem per field; RegistrationForm.outstanding(...) lists only what is genuinely missing; the button is live whenever a submission is not in flight. Pressing it with a bad form shows the named problems. No submit control anywhere depends on a backend address.
  2. The address left the tourist's path. It now lives in Settings → Backend connection (advanced), where Test connection performs a real GET /api/v1/health — Connected is claimed only when something actually answered, and an address with nothing behind it reports Offline.
  3. A build-time default, seeded exactly once. -PAUTHORITY_URL (or TSM_AUTHORITY_URL, or AUTHORITY_URL= in local.properties) becomes BuildConfig.DEFAULT_AUTHORITY_URL; AppContainer.start() writes it through seedBaseUrlIfUnset, which is a no-op once an address exists. This pass's APK carries http://192.168.1.102:8080, so a first launch on this machine's Wi-Fi is already pointed at the server.
  4. Two roles, two sessions. The app opens on a Welcome screen offering I'm a tourist and I'm an authority officer; a returning tourist with a valid session is offered Continue above the choices. Officer and tourist sessions are stored under separate keys in the same DataStore, so an officer sign-in cannot make the phone behave like a tracked tourist and either sign-out leaves the other alone. Both are restored on restart.
  5. The boundary is the server's. The officer console reads GET /api/v1/authority/tourists, which already required require_auth("authority"). Hiding a screen proves nothing, so the live test presents a tourist token to that route and asserts 403.
  6. The backend configuration screen survived as the advanced/technical screen (address, connection state, queue + upload now, tourist profile, PIN change, the authority's view of this phone), with sign-in and registration removed from it.

16.4 A refactor with a reason

DataStoreAuthoritySessionStore took a Context only to derive a default DataStore, which made it untestable off-device. It now takes the DataStore directly, with createAuthoritySessionStore(context) as the production factory. That is what turns "the session survives a restart" and "the officer session is separate" from asserted-by-inspection into asserted: AuthoritySessionStoreTest drives a real PreferenceDataStore over a throw-away file on the plain JVM, with no Robolectric. The file's handle is released by joining the cancelled scope before a second store opens the same file — without that the test would be racy.

17. Round: the phone could never reach the authority — Android's cleartext block (2026-10-18)

17.1 The report

Two screenshots from a real phone, both taken on the phone itself, both showing a red banner:

  • Tourist sign-in: "The authority at http://192.168.1.102:8080 is not answering. Check that the server is running and that this phone is on the same Wi-Fi network." — with the connection card reading Status: Offline, "No answer from http://192.168.1.102:8080."
  • Authority officer: "Cannot reach http://192.168.1.102:8080: Cleartext HTTP traffic to 192.168.1.102 not permitted".

The second banner is the tell: it is not a message this app writes. It is the wording Android itself uses when the platform refuses to send a plain-HTTP request.

17.2 The root cause, exactly

  • The authority is the project's own server: plain HTTP on port 8080 over the LAN (http://192.168.1.102:8080). There is no TLS.
  • The app sends it with HttpURLConnection (HttpUrlConnectionAuthorityHttp), and the transport wraps any IOException as AuthorityCall.Unreachable, whose message is shown verbatim as "Cannot reach
    : ".
  • Android 9 (API 28) and later refuse cleartext HTTP by default for any app whose targetSdk is 28 or higher. This app's targetSdk is 35, and the manifest declared neither android:usesCleartextTraffic nor android:networkSecurityConfig.

So the request was killed by the network-security policy before it reached the network. The server was never asked, never answered, and never logged anything — which is exactly what the authority's own access log shows: across the whole session there is not one request from the phone's address, only the host's own browser on the dashboard. The tourist screen's "is not answering" is the same failure with the platform's message summarised away; the officer screen happened to print the raw sentence.

This had been true since the first build. It is not a regression from the two-role round, and no amount of restarting run.py would ever have changed it.

17.3 The fix

  1. app/src/main/res/xml/network_security_config.xml (new) — a <base-config cleartextTrafficPermitted="true"> with the reasoning written down in the file, so the next reader does not "harden" it back into a broken state. The file also says what to do if the authority ever gains TLS.
  2. AndroidManifest.xml — the <application> now declares android:networkSecurityConfig="@xml/network_security_config".
  3. NetworkSecurityConfigTest (new, 3 tests) — reads the shipped manifest and the profile and fails if the manifest stops pointing at a profile, if the profile stops permitting cleartext, or if the manifest re-blocks it with usesCleartextTraffic="false". A build setting that silently disables the app's only way to reach its backend deserves a test, not a comment.

Nothing else changed: the address resolution, the tourist/officer sessions, the officer endpoint and the require_auth("authority") boundary from round 16 are untouched.
