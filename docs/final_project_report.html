2. What was wrong (diagnosis)

2.1 The Create Geo-Fence map was blank with no Google key

ui/components/SafetyMap.kt gated the entire map on mapsApiKeyConfigured (BuildConfig.MAPS_API_KEY non-blank). With no key it rendered a "missing key" notice instead of a map, so taps never reached onMapClick, no vertices could be added, "Close ring" stayed disabled, and zones could not be saved. The key plumbing itself was correct; only the no-key path was broken.

2.2 Home contradicted itself: "Tracking: Active" but "Background service: Not running"

HomeScreen.kt printed snapshot.backgroundTracking, which is only the intent flag set by TrackingController.start(backgroundTracking = …). It never reflected whether LocationTrackingService was actually alive, and it conflated three distinct states (tracking on / service on / service wanted-but-blocked).

2.3 No delivery path for alerts or SOS

There was no persistence for outbound events and no transport, so an alert or SOS generated while offline had nowhere to go. There was also no backend server in this repository — that gap is now closed: backend/ is a working Flask + SQLite service with an operator dashboard, and the app has a real transport wired to it (deliverable 13 and 14 below, and docs/progress_log.md §12).

3. Deliverable 1 — Key-less map (OpenStreetMap fallback)

Design. When a Google Maps key is present, the app uses Google Maps exactly as before. When it is absent, SafetyMap.kt renders OfflineOsmMap, a self-contained Compose canvas that:

  • fetches standard OpenStreetMap raster tiles;
  • projects lat/lon to screen with a pure, unit-tested MercatorProjection (integer zoom levels so tiles and geometry align exactly);
  • supports pan/zoom/tap gestures and the same tap-to-add-vertex flow;
  • degrades to a graticule grid if tiles cannot be fetched (offline), so the screen is never blank and zones can still be drawn and saved.

Honesty. The projection maths is proven by MercatorProjectionTest (11 tests: known slippy-map tile indices, screen↔world round-trips, ground resolution at the equator, latitude clamping, panning). Whether tiles visually load is NOT EXECUTED — this environment has no device/emulator and no way to observe rendering. Do not treat the map as device-verified.

5. Deliverable 3 — Offline outbox + pluggable transport

Design. Every alert/SOS is written to a durable local outbox first, then handed to a SyncTransport.

  • Durable: table outbox_events, added by an additive migration (MIGRATION_1_2); existing zones and history are not erased.
  • Exactly-once semantics on the client: idempotent enqueue on a stable dedupe key; delivered rows leave the pending queue; permanent rejections are marked failed; transient failures stay pending and increment the attempt count.
  • Honest transport, now real: SyncTransport is an interface. The shipped SelectingSyncTransport delegates to the real HTTP authority transport when a base URL is configured and to NoBackendTransport (which returns Retry) otherwise. The app never claims a message was delivered when it wasn't — with no address configured the status reads "Queued (offline)"; with an address it reports the server's actual verdict.

Schema changes are versioned (AppDatabase.VERSION = 3): MIGRATION_1_2 adds the outbox and MIGRATION_2_3 adds the emergency-contact table, both additive, with no fallbackToDestructiveMigration(); each migration's SQL was verified against the generated N.json and is executed on the JVM by RoomPersistenceTest.

7.1 Dataset (real, verified)

Microsoft Research GeoLife GPS Trajectories 1.3 — the official archive was downloaded and unzipped here (313,164,406 bytes, 298.7 MB). Measured scale: 182 user directories, 18,670 .plt files, 24,876,978 data lines, 0 malformed rows. The guide claims 17,621 trajectories while the archive contains 18,670 — both are reported. No open-source licence is bundled; use is research-only with the required citation.

7.2 Verified schema and a real data quirk

.plt = 6 header lines + CRLF + 7-token data lines; the two independent time encodings agree to within 4.8×10⁻⁶ s. Critical quirk: .plt file names collide across users (847 ids shared), so every grouping uses traj_uid = user_id | trajectory_id — otherwise different people's trajectories would silently merge (a leakage bug).

7.3 Cleaning & EDA

Cleaning removes unparsable timestamps, out-of-range/null-island coordinates, duplicate (trajectory, timestamp) rows (698,900 removed), sorts and segments on gaps > 120 s, and flags GPS jumps (> 60 m/s). EDA produced 12 figures + 11 tables + a findings document from real values (e.g. median sampling interval 2.00 s; median speed 3.23 m/s; busiest hour 09:00). Full detail in docs/dataset_and_eda.md.

7.4 Model

Unsupervised sklearn.ensemble.IsolationForest (200 trees, seed 42 — reproducible) over 14 standardised movement features. Output = movement anomaly score (higher = more unusual), not a probability and not danger. Training used a 1,200-trajectory fixed-seed sample, split by traj_uid (900 train / 300 test, 0 overlap).

7.7 Movement recognition and impact detection — UCI HAR (supervised, shipped on the device)

The GeoLife work above is GPS-only and unsupervised: it can say "this trajectory is unusual", which is not the same as what the person is doing or whether they just fell. That needed a second, supervised pipeline on a sensor dataset — the UCI HAR dataset listed in DATASETS.pdf.

Two scikit-learn models are trained, exported to JSON, shipped in assets/, and walked on the phone by hand-written Kotlin (motion/DecisionForest.kt). No TensorFlow / TFLite / PyTorch, and no network at inference time — the two models together are under 330 KB, which is why a hand-written walker was chosen over a runtime.

Features. The phone computes 24 time-domain features (MotionFeatures.kt) that mirror the Python extractor exactly, in the same order — validated on both sides of the wire. Accelerometer samples are converted to g by dividing by 9.80665 m/s² so the units match the dataset. The 561 UCI features (FFT energy bands, entropy) are not computable in real time on a phone.

Model A — activity recognition (real human labels). Random forest, 32 trees, depth 8.

Model Features Accuracy Macro-F1
Shipped on-device model 24 0.8351 0.8333
561-feature reference 561 0.9287 0.9271

Adding the three per-axis means (the gravity direction, i.e. how the phone is held) is what carried the on-device model to 0.8351; the three walking variants are the confusion, and the app only ever asks the model the coarser question "is this person moving?" Model B — impact / fall-signature detector (synthesised positives). Random forest, 40 trees, binary.

UCI HAR contains no falls. There is no fall class, no impact annotation and no subject who fell. So the positive class was manufactured: a fall-like transient (short free-fall dip, impact spike of several g, then stillness) was injected into real recorded windows from the held-out subjects; the negative class is those same recordings untouched.

The last row is what gives the others meaning: the identical pipeline on randomly permuted labels collapses to chance, so the near-perfect score is the detector finding the injected signature in real held-out recordings — not leakage or a label-encoding feature. It is still not a fall-detection claim: an injected impact is a large stereotyped transient, and a real fall can be gentle or look like sitting down quickly. The named upgrade path is SisFall / UniMiB SHAR / MobiFall (real falls), and it has deliberately not been claimed as done. The detector's score is also never sufficient on its own — see §7.9.

An exporter bug was caught before it shipped: scikit-learn's tree_.value holds class fractions, not counts, so np.rint(tree.value) collapsed every leaf to a one-hot vector. The model would have loaded, run, and answered — just wrongly. Fixed to np.rint(tree.value * tree.weighted_n_node_samples), with a pytest regression guard, and the exported JSON is verified against scikit-learn (max probability error 4.97e-07, 0 argmax mismatches) both in Python and, independently, in Kotlin against the shipped asset.

Full method, per-class tables, embedded confusion matrices, limitations and the reproduction commands: docs/model_card_movement.md.

7.8 Historical risk analysis on approach — deliberately not a model

When the tourist comes within 200 m of a restricted or dangerous boundary, the Tracking screen now shows an approach briefing: the zone, the distance, the tourist's own recorded crossings of that zone, and a 0–100 risk score with every factor itemised and explained.

The score is a published weighted checklist (ApproachRiskModel), not a learned danger probability: zone severity (DANGEROUS 40 / RESTRICTED 28 / SAFE 5), 3 points per crossing in the last 7 days capped at 18 (4 points for never-visited ground), proximity up to 16, night 12 / dusk 5, ambulating 4, and the live impact score 12 above threshold (6 neutral when no model is available). Bands are LOW < 30 ≤ MODERATE < 60 ≤ HIGH.

It is deliberately not dressed up as a probability, because the app has no labelled outcome data and there is nothing to fit. The weights live in one place and are unit-tested (26 tests across ApproachRiskTest, ZoneHistoryTest, ApproachBriefingTest), including the invariants that the score never exceeds 100 and that the listed factors account for every point of it. The card says this to the user's face rather than only in the docs.

7.9 How a fall is actually decided on the phone

The model's score is one of three gates, and all three must agree before anything is reported:

Gate Threshold Why
Impact magnitude ≥ 2.0 g a hard fall lands roughly 2–5 g; below that it is a stumble or a dropped phone
Model score ≥ 0.55 the window looks like the trained impact signature
Stillness after the impact std ≤ 0.12 g measured from the last sample at or above the impact threshold, so the impact plateau itself is not mistaken for stillness
Cooldown 15 s overlapping windows mean one fall would otherwise raise five alerts
Tail fraction 0.25 if the peak lands in the final quarter there is not enough signal to judge stillness, so that gate is skipped, not failed

Consequences visible in the UI: the face shows the probability and its threshold, the peak g, the stillness value and its threshold, and it says "suspected". A high model score with no physical impact raises nothing, and no SOS is ever sent automatically.

7.10 A genuine supervised future risk prediction — on-device, and honest about its basis

Everything above is either a configured rule (§7.8's approach checklist) or a detector that reacts to an impact that has already happened (§7.9). This round adds the third, genuinely different thing the brief asked for: a trained model that predicts an event before it happens, and it deliberately does not pretend the project's four named datasets can support it.

The dataset problem, stated plainly. GeoLife, UCI HAR, OpenStreetMap and OpenWeatherMap/Open-Meteo contain no outcome labels at all — no injuries, no incidents, no falls. A supervised tourist-incident model cannot be trained from them, and inventing labels would be fabrication. The honest options were to find a dataset with real outcome labels or to ship nothing; this round did the former and documents the swap.

The dataset actually used. UniMiB SHAR (Micucci, Mobilio, Napoletano, 2017) — 30 subjects, 9 activities of daily living and 8 real fall types, 50 Hz phone accelerometer, with real recorded falls. 1,980 trials were read; 1,979 used. One recording (subject 10, Jumping, trial 1) contains 9,369/9,624 non-finite values and was dropped, counted and reported, not repaired. The dataset has no OSI licence; the provenance file says so rather than inventing one. Full provenance is in docs/future_risk_prediction.md §2.

The target and the horizon. IMMINENT_FALL = a hard fall impact lands within the next second. Impact instant = argmax(magnitude) of the trial, accepted at ≥ 2.0 g (the app's own FallPolicy.MIN_IMPACT_G); 6 fall trials never reach 2 g and are excluded and counted. Horizon and feature window are both 50 samples = 1.0 s, chosen because fall trials run 151–446 samples with the impact around index ~120, leaving ≥ 95 pre-impact samples — so 1.0 s is the longest fully supported horizon, not a round number. A 30-minute horizon is explicitly not attempted, because no accelerometer can see 30 minutes ahead.

No leakage, checked not asserted. A window ending at t uses samples [t-49, t]; the label asks about (t, t+50]. The two intervals are disjoint, train.check_no_future_information() re-derives that from the raw recordings on every run, and a shuffled-label control (same features, same pipeline, permuted labels) scores ROC-AUC 0.477 — chance, as it must be if nothing leaks.

Method. Subject-disjoint 60/20/20 split, seed 42, 30 subjects → 18/6/6 (disjoint: true); 51,128 windows (6,458 positive / 44,670 negative); class_weight="balanced_subsample". No scaler is fitted at all — every feature is scale-free within its own window — so there is no fitted preprocessing step that could carry a global mean from train to test. Validation subjects were used only for the Platt calibration, the two band thresholds and the hyper-parameter search; the test subjects were scored once.

Calibration. Platt scaling on logit(p_forest), fitted on the validation split only (a = 1.249403, b = −1.079049), improves the Brier score from 0.062600 → 0.056675. The reliability table is published including the bins that are over-confident (0.2–0.4), because hiding them would be the dishonest choice. Bands: HIGH ≥ 0.314046 (validation max-F1) and MODERATE ≥ 0.069201 (largest validation threshold keeping recall ≥ 0.95), both fitted on validation and shipped inside the artefact.

Where inference runs: on the device. The model reuses the app's existing DecisionForest JSON walker (the only change is an optional expectedFeatures parameter so a 22-feature model loads without weakening the existing 24-feature check) — no new ML framework, runtime or format was added. It is fed by the same acceleration subscription the movement watch already owns, taking the last 50 samples of each window, so there is no second listener and no extra battery cost. That makes the tourist-facing prediction work fully offline, and means no accelerometer data leaves the phone.

Three things kept visibly apart. The app now shows, as separate cards: the configured geofence status, the approach-risk checklist (§7.8, a published heuristic with no probability), and the future risk prediction (this model — the only one of the three that is trained, and the only one that shows a probability). The card's own text names the other two and denies being them; it carries the non-causal caveat for its factor list and states that it never sends an SOS by itself. Both sentences are asserted by tests, and backend/tests/test_risk.py asserts that a HIGH prediction leaves latestSos empty and state != "SOS" — risk can never raise an SOS.

What reaches the authority. A throttled summary (never raw sensor data) travels through the existing offline outbox as a new OutboxKind.RISK event with origin = ON_DEVICE_MODEL (isSimulated = false): first elevated band, any escalation, a 120 s refresh, and one "cleared" record when the band drops back to LOW. UNAVAILABLE and stale bands are never sent; the backend rejects UNAVAILABLE outright. Predictions are stored in their own risk_assessments table and shown in their own dashboard panel and tiles (GET /api/v1/authority/risk, per-tourist history, latestRisk) — never mixed into the SOS queue or the incident feed. This is what the earlier round's database gap was about: the dashboard previously had no table that could hold a prediction, so it neither received nor displayed one.

The honest bottom line. This is a real model, with real held-out numbers, real leakage controls and a real on-device path — and it is not a deployment-ready fall alarm. 5.09 false alarms per minute of ordinary movement, mid-range probabilities that are over-confident, lab-recorded data from 30 adults, and an untestable phone-drop-vs-person-fall failure mode are all in the model card. It is reported to the tourist as an informational state and to the authority as a labelled prediction, and it changes no operational state.

Not verified: the card's rendering on a real screen and the whole sensor→forest→card chain on real hardware. No emulator, AVD or device exists in this environment (adb devices is empty); the wording is instead pinned by FutureRiskCardModelTest (18 tests) and the inference by FutureRiskReferenceTest, which replays the shipped asset against scikit-learn's own probabilities for 16 real held-out windows.

Full model card, dataset provenance, measured metrics, calibration table, false-alarm breakdown and the complete limitations list: docs/future_risk_prediction.md. Everything is reproducible with python ml/future_risk/train.py and powershell -File ml\run_all.ps1 -FutureRisk.

7.11 Self-service tourist registration — the tourist creates their own account

Every tourist account in this project until now was created by an officer at the dashboard, and the tourist signed in with an id and a one-time password. That is the wrong shape for a tourist who simply installs the app: with nobody at a desk, there was no way to start. This round adds the missing journey — register from the phone — and makes the result visible to the authority without any officer action.

The ID is minted by the database, not the client. A client-side counter is the classic bug here: two phones registering in the same second both compute "00124". Instead a new table, tourist_id_sequence (id INTEGER PRIMARY KEY AUTOINCREMENT, issued_at INTEGER NOT NULL), is the ledger: each registration consumes one row and reads the number SQLite issued. The text id is TR-<current UTC year>-<5-digit number> — e.g. TR-2026-00124 — and because tourists.id is a primary key, even a text collision cannot produce a duplicate: the code steps over to the next number. The counter is never reset, across years or restarts. test_registration.py registers twelve tourists in a row (twelve distinct ids) and forces a collision to prove the step-over.

The PIN is the credential, and nothing secret is returned. Self-registration keeps the existing NOT NULL password_salt / password_hash schema (no migration risk to existing rows) by writing a random, immediately discarded secret into those columns; the account's real credential is the PIN, through the project's existing scrypt hash_password. The response contains only the id and the account's public fields — no token, no password, no PIN, no salt, no digest — and registering does not sign anybody in. The tourist signs in as a separate step with the id and the PIN they chose.

One public write, and the escalation it refuses. POST /api/v1/auth/register creates only tourists rows, reads no privilege field (a body carrying "role": "authority" is 400, and there is no field that could grant one — the path does not exist rather than being blocked), issues no session, and treats a phone number that is already registered as 409. Validation is pure and lives in one place, backend/tsm/registration.py, reusing hash_password and the same contacts validator the outbox uses, so a contact accepted here is a contact the sync path would accept.

The app. The Authority screen's sign-in card gained two deliberate modes — Sign in and Register as tourist. The form collects a name, phone number, a chosen PIN and its confirmation, and any number of emergency contacts (added one at a time, removable). It is validated on the phone first (a mistyped confirmation is answered instantly, with no round-trip) and the server's 409 is shown as "already registered" rather than a generic failure. On success the card becomes a registration-success screen showing the id in a monospace readout with a Copy Tourist ID button, plus a plain-language instruction on how to sign in next (RegistrationForm.kt, AuthorityContract.kt/AuthorityApi.kt/AuthorityClient.kt, AuthorityViewModel.kt, ui/screens/AuthorityScreen.kt).

The dashboard. GET /api/v1/authority/tourists was enriched additively and the panel became "Registered Tourists". Each row separates three different facts that used to be conflated:

  • registration — is this a real account? (registrationStatus, registeredAtMillis, registrationSource: SELF for an app registration, the officer's id for a desk account, null older);
  • tracking — have we heard from the phone? (trackingStatus, lastSeenMillis, hasPosition, latestPosition);
  • safety — openSosCount, latestRiskBand, latestRiskAtMillis (unchanged in meaning).

A tourist who has registered but never reported reads "Location not yet available"; a position is never invented. New registrations appear at the top of the newest-first list on the next refresh, with no officer action.

A latent bug found on the way. While extending the register, the RISK ingest was found to insert its risk_assessments row outside the with db().write() block that inserted its events row, so a prediction and its audit entry could commit separately. It now runs in the same transaction. The prediction itself is unchanged.

7.12 Two-role sign-in, and the button that was dead on a fresh install

The reported symptom. On a phone with a fresh install, the app opened on the Authority screen with NOT SIGNED IN and both Sign in with PIN and Create my account greyed out. Nothing on the screen explained why, and no Tourist ID was ever generated.

The root cause, exactly. Those two controls — and Save address — were enabled with

enabled = !busy && address.isNotBlank()

and address was seeded from the stored session's baseUrl, which is empty on a fresh install. So the first thing a new user saw was three dead buttons whose only requirement was an address that the app never asked for and never explained. It was not a registration bug and not a credential bug: the submission controls were gated on a field the tourist was never meant to fill in. Two further consequences fell out of the same code: the sign-in and registration flows lived on the same screen as the operator's backend configuration, and a tourist could reach the authority configuration at all.

The fix.

  1. The gate moved to form validity. RegistrationForm.fieldErrors(...) now reports a problem per field and RegistrationForm.outstanding(...) lists only what is genuinely missing; the button is live whenever the form is not in flight, and pressing it with a bad form shows the named problems instead of doing nothing. No submit control anywhere depends on a backend address.
  2. The address left the tourist's path. It lives in Settings → Backend connection (advanced), where Test connection performs a real GET /api/v1/health — Connected is reported only when something actually answered, and an address with nothing behind it reports Offline.
  3. A build-time default, seeded once. -PAUTHORITY_URL (or TSM_AUTHORITY_URL, or AUTHORITY_URL= in local.properties) becomes BuildConfig.DEFAULT_AUTHORITY_URL; AppContainer.start() writes it with seedBaseUrlIfUnset, which is a no-op when the user has already chosen an address. The APK attached to this pass carries http://192.168.1.102:8080, so a first launch on this machine's Wi-Fi is already pointed at the server.
  4. The two roles became two sessions. The app opens on a Welcome screen with I'm a tourist and I'm an authority officer; a returning tourist with a valid session is offered Continue above the choices. Tourist and officer sessions are stored under separate keys in the same DataStore, so an officer sign-in does not make the phone a tracked tourist, and either sign-out leaves the other alone.
  5. The role boundary is the server's. The officer console reads GET /api/v1/authority/tourists, which already required require_auth("authority"). Hiding the screen in the app proves nothing; the live test presents a tourist token to that route and gets 403 (§9).

What was run for this round. 7.13 The phone could never reach the authority — and it was Android, not the server

The report. Two screenshots taken on a real phone. The tourist sign-in screen showed the red banner "The authority at http://192.168.1.102:8080 is not answering. Check that the server is running and that this phone is on the same Wi-Fi network." and the connection card read Status: Offline. The officer screen showed the same address with the raw sentence "Cannot reach http://192.168.1.102:8080: Cleartext HTTP traffic to 192.168.1.102 not permitted".

The root cause, exactly. The second sentence is not written by this app — it is Android's. The app talks to its authority over plain HTTP (http://192.168.1.102:8080); the client wraps any IOException as Unreachable and prints the platform's message verbatim. Android 9 (API 28) and later refuse cleartext HTTP by default for any app whose targetSdk is 28+, this app targets 35, and the manifest declared neither android:usesCleartextTraffic nor android:networkSecurityConfig. The request was therefore killed by the network-security policy before it reached the network: the server was never asked, never answered, and never logged a request from the phone — which is precisely what its access log shows. The tourist screen's softer "is not answering" is the same failure, summarised. This was true from the first build; restarting run.py could never have changed it.

The fix.

  1. app/src/main/res/xml/network_security_config.xml (new) — a <base-config cleartextTrafficPermitted="true">, with the reasoning written into the file so a later "hardening" pass cannot silently re-break the app, plus what to do if the authority ever gains TLS.
  2. AndroidManifest.xml — the <application> now declares android:networkSecurityConfig="@xml/network_security_config".
  3. NetworkSecurityConfigTest (new, 3 cases) — reads the shipped manifest and profile and fails the build if the manifest stops pointing at a cleartext-permitting profile, or re-blocks it with usesCleartextTraffic="false".

What was run for this round. Android JVM 548 tests, 0 failures, 0 errors, 7 skipped across 50 classes (+3, all NetworkSecurityConfigTest). The backend (265), acceptance (41/41) and ML (179) suites were re-run unchanged and stayed green. The built artefact was verified directly: aapt2 dump xmltree shows android:networkSecurityConfig(0x01010527)=@0x7f0c0002 on <application>, and aapt2 dump resources resolves 0x7f0c0002 to res/xml/network_security_config.xml, whose bytes contain cleartextTrafficPermitted. The opt-in live suite was not re-run this round (the backend was stopped), so its seven cases skip in this run; their last measured result is §7.12's 7/7.

Not verified: that the banner actually clears on the phone — that needs the new APK installed on a real device (INST-24/25). What is proven is that the artefact now contains the policy Android requires, and that the setting cannot silently regress without a failing test.

8.1 What the app sends

A new authority client (app/src/main/java/com/touristsafety/app/authority/) speaks the backend's HTTP contract: a hand-written JSON codec (Json.kt — used instead of org.json, which returns nulls on the plain JVM, so the whole client stays unit-testable), the wire codec, an HttpURLConnection layer, and a durable transport. Emergency contacts are uploaded through the durable outbox (OutboxKind.CONTACTS), not a direct PUT, so an offline edit still syncs when the network returns.

8.2 The delivery rules (why a mistake cannot lose an event)

The mapping from a server verdict onto the outbox is deliberately biased: only a permanent rejection discards an event.

Server outcome Outbox result Why
DELIVERED Delivered (ack id) stored by the authority
DUPLICATE Delivered idempotency — the server already has it
REJECTED (or 400/422) Rejected with the reason the same bytes can never be accepted
401 / 403 Retry re-signing-in will deliver it
404 / 409 / 5xx / IO / malformed Retry could be a misconfiguration — never discard

8.3 The backend and the dashboard

backend/ is one Flask app over one SQLite file, serving both the phone API and a static operator dashboard at /. It generates its own credentials on first start and writes them once to backend/var/DEV_CREDENTIALS.txt; no password is written into the source, and test_security.py asserts that. The events table is append-only with a UNIQUE (tourist_id, dedupe_key) index — that index is what makes re-delivery harmless — and an SOS has its own table because it has a workflow (OPEN → ACKNOWLEDGED).

Run it with python backend\run.py; the dashboard is then at http://127.0.0.1:8080/. 12. Limitations & blockers (stated, not hidden)

  1. No device/emulator here. Map tile rendering, the crash fix, the new movement/approach cards, live sensor inference, the backend/contacts screens, the new Welcome, tourist sign-in / create-account and officer console screens, and all androidTest sources (including the migration test) are NOT EXECUTED — compile- and JVM-checked only. adb devices is empty. Recorded as INST-16…INST-25 in docs/test_report.md.
  2. The backend exists, but the device's own path to it is unproven. backend/ is a working Flask + SQLite service with an operator dashboard, and the production Kotlin client was driven against it on the JVM (41/41 acceptance + 7/7 live). What has not been done here is the same flow from a device — its HttpURLConnection, emulator loopback 10.0.2.2 / Wi-Fi routing, and the Compose sign-in, create-account, role-chooser and officer-console screens (INST-20, INST-21, INST-24, INST-25). Routine POSITION reporting now exists (behind an explicit interval/distance policy) but its on-device GPS has not been run here. No SOS is ever sent automatically.
  3. The movement impact detector uses no real falls. UCI HAR contains none, so that detector's positives are synthesised impacts injected into real recordings; its 0.9999 ROC-AUC measures detection of that injected signature, not clinical fall detection. Controls are in docs/model_card_movement.md. This is no longer true of the future-risk model: §7.10's predictor is trained on real recorded falls, and its 0.764569 PR-AUC / 0.929577 trial sensitivity are real held-out numbers — but they are still fall numbers from a lab, not tourist-incident numbers, and it is not a deployment-ready alarm (5.09 false alarms per minute of ordinary activity; see item 10).
  4. GeoLife has no real anomaly labels. Accuracy/F1 against real anomalies is impossible; only an injection-based ROC-AUC (0.8922) is reported, and the trajectory model is unsupervised by design. The output is a movement anomaly score, never danger.
  5. The approach-risk score is a weighted checklist, not a fitted model. Published weights, unit-tested, and labelled as such in the UI. It has no labelled outcome data to learn from.
  6. Geographic bias in the GeoLife data (dominated by a few Beijing users), and placement bias in UCI HAR (30 volunteers, waist-mounted phone) mean "normal" is region-, person- and posture-specific.
  7. The key-less map is not Google Maps. Real Google tiles require the user's own API key (docs/google_maps_setup.md); without one, the app uses key-free basemaps (OpenStreetMap by default, with Esri and OpenTopoMap as fallbacks). CARTO Voyager was tried and removed because it now serves a watermark instead of a map, so it is not offered at all.
  8. PDF/HTML are best-effort exports. Every document has a sibling .html and .pdf in docs\ (README.html/README.pdf live in the repository root) (Markdown → HTML via python-markdown → PDF via headless Microsoft Edge --print-to-pdf). All companions were regenerated on 2026-10-18, including the new docs/future_risk_prediction.html/.pdf, so they match the Markdown of this round. Prefer the Markdown as the source of truth. The PDFs embed the model-card figures from ml/outputs/har/**, so the .md and the figures must be copied together.
  9. This is a monitoring aid, not an emergency service: it does not contact anyone automatically.
  10. The future-risk model is not a deployable fall alarm. Measured on held-out subjects it raises 5.09 false alarms per minute of ordinary activity at the app's cadence (16.30/min at the raw window stride), concentrated in jumping (0.161), sitting down (0.156) and lying down (0.127); its mid-range probabilities (0.2–0.4) are over-confident; it was trained on 30 healthy adults in a lab carrying or pocketing a phone, never on a tourist outdoors; it forecasts one second ahead and nothing longer; and it cannot distinguish a dropped phone from a falling person (no phone-drop activity exists in the dataset, so that failure mode is untested). It is not the best model in the repository — hist_gradient_boosting reaches PR-AUC 0.8150 but cannot be walked on-device. A HIGH band is an informational UI state and a queued summary: it raises no alarm, changes no operational state, and never sends an SOS. Full detail in docs/future_risk_prediction.md.
  11. The future-risk card has never been rendered on a screen. No device or emulator exists here, so the Compose card, the real sensor→forest→card chain and the dashboard's new predictions panel are NOT EXECUTED (INST-22). The wording is instead pinned by FutureRiskCardModelTest (18 tests) and the inference by FutureRiskReferenceTest, which replays the shipped asset against scikit-learn's own probabilities on 16 real held-out windows.
